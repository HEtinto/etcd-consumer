# 消息队列比较

## 总览

| 维度     | Kafka                       | RocketMQ                 | RabbitMQ             | Redis                        | Etcd                         |
| :------- | :-------------------------- | :----------------------- | :------------------- | :--------------------------- | :--------------------------- |
| 定位     | 大数据日志/流处理平台       | 金融级/互联网业务 MQ     | 通用型标准消息代理   | 缓存 / 轻量级队列            | 分布式协调服务 (非专业 MQ)   |
| 吞吐量   | 极高 (百万级 TPS)           | 高 (十万级 TPS)          | 中等 (万级 TPS)      | 极高 (但在队列模式下受限)    | 低 (受限于 Raft 协议)        |
| 延迟     | 毫秒级                      | 毫秒级                   | 微秒级 (极低)        | 微秒级 (内存操作)            | 毫秒级 (写入慢)              |
| 可靠性   | 高 (多副本, 易丢数据需配置) | 极高 (支持同步刷盘)      | 高 (ACK 机制完善)    | 一般 (取决于持久化配置)      | 极高 (强一致性)              |
| 功能特性 | 消息回溯、流处理            | 事务消息、顺序消息       | 路由灵活、管理界面好 | 简单、支持 Pub/Sub 和 Stream | 监听机制(Watch)、租约(Lease) |
| 运维成本 | 高 (依赖 ZK 或 KRaft)       | 中 (Java 开发，生态较新) | 低 (Erlang，稳定)    | 极低 (通常已有)              | 中 (Go 编写，二进制部署)     |

### 💡 总结：怎么选？

* **追求极致吞吐、搞大数据/日志** **→ 选**  **Kafka** **。**
* **搞电商/金融、需要事务支持、怕消息堆积** **→ 选**  **RocketMQ** **。**
* **中小规模、路由规则复杂、追求低延迟** **→ 选**  **RabbitMQ** **。**
* **项目已有 Redis、不想维护新组件、任务不重要** **→ 选**  **Redis (Stream)** **。**
* **只需要做配置通知、或者极低频的任务调度** **→ 勉强可以用** **Etcd** **(但不要用来传大数据)。**

### docker-compose 文件解释

创建了一个三节点etcd集群，三个节点的 etcd 端口映射关系为 2379(本地)->2379(etcd0容器), 2381(本地)->2379(etcd1容器), 2383(本地)->2379(etcd2容器).

使用命令 `etcdctl --endpoints=http://localhost:2381 put /messages/ "world"` 可以向 etcd1 容器中的 etcd 服务发送 put 请求. 请求将被消费者程序处理, 消费者有3个, 分别是 consumer0, consumer1, consumer2, 由 mian.go 程序实现.
